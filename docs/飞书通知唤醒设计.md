# 飞书通知唤醒设计

## 结论

方案可行，但应使用 Android 的事件式通知监听，而不是循环轮询通知栏。

飞书自定义机器人负责把一条唤醒消息推送到专用群；服务器手机上的飞书客户端负责
接收厂商系统 Push；RootSync 通过 `NotificationListenerService.onNotificationPosted()`
收到通知事件并解析协议。这样待机时不需要保持 RootSync 的公网长连接。

## 建议流程

```text
用户端 B 启动临时 rsync send/receive
  -> 生成 requestId、nonce、expiresAt
  -> POST 飞书机器人 Webhook
  -> 飞书向服务器手机 A 推送群通知
  -> A 的 NotificationListenerService 收到通知
  -> 校验消息、配对设备、时效和局域网地址
  -> A 主动连接 B
  -> 执行保存于 A/B 设备配置中的同步策略
  -> 返回完成结果并销毁一次性 requestId
```

## 唤醒消息字段

```json
{
  "protocol": "ROOTSYNC_WAKE_V1",
  "serverId": "目标服务器设备 ID",
  "clientId": "发起设备 ID",
  "clientIp": "192.168.1.23",
  "clientPort": 8873,
  "requestId": "一次性 UUID",
  "nonce": "随机数",
  "expiresAt": 1786280000,
  "action": "CONNECT_TO_CLIENT",
  "mac": "HMAC-SHA256"
}
```

通知文本应使用固定前缀和紧凑的 Base64URL 载荷，避免飞书对普通文本的格式化影响。

## 必须满足的条件

- 用户在系统设置中授予 RootSync“通知使用权”。
- 飞书通知内容必须允许显示，而不是只显示“收到一条新消息”。
- 专用群不能静音，飞书通知渠道不能关闭。
- 小米系统中允许飞书自启动和接收通知；RootSync 的通知监听服务不能被限制。
- A 与 B 必须位于可互通的局域网；消息中的 IP 必须验证属于当前局域网。

## 安全设计

- 飞书 Webhook 地址和签名密钥存入 Android Keystore 加密配置。
- 同步协议再使用每设备独立配对密钥，不能只依赖飞书消息。
- 请求有效期建议 60 秒，时钟误差窗口不超过 30 秒。
- 每个 `requestId` 只处理一次，持久化最近已处理 ID 防止重放。
- 只接受已配对 `clientId`，并验证通知来自飞书包名和指定会话标题。
- 不在飞书消息中直接发送 rsync 长期密码。
- 真正连接后增加一次 challenge-response，确认发起端持有配对密钥。

## 可靠性处理

- 飞书通知可能被折叠、延迟、隐藏正文或重复投递，因此需要请求超时和去重。
- 客户端发送机器人消息后应同时保留局域网 UDP 直连作为快速路径。
- 服务器未响应时采用短退避重试，例如 3 秒、8 秒、20 秒，共三次。
- 服务器连接成功后客户端停止重试，超时后关闭临时 rsync 服务。

## 功耗

`NotificationListenerService` 由系统在通知到达时回调，不需要保持循环线程、WakeLock
或高频定时器。待机功耗主要由飞书自身 Push 和系统通知链路产生，RootSync 的增量
消耗通常只出现在收到唤醒消息后的短时间解析与连接阶段。
